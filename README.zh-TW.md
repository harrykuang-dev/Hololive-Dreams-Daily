# hololive-Dreams 日常

以 MaaFramework、MFAAvalonia 與獨立執行的 Holodori-Auto 模組建立的 Windows 日常程式。Live 僅使用遊戲內建 Auto；資源消耗可設定，不自動補充資源。

目前仍在開發。原始碼包含任務設定介面、錄影畫面辨識、Auto 檢查、結果紀錄、導航基礎與子程序管理；完整日常執行及可攜打包尚未驗收。預設只勾選連接遊戲。

新設定的預設值會關閉任務失敗後繼續執行，既有設定保留原值。錄影恢復已驗證釣魚失敗結果、兩位數能量調整、活動 Live 結果導航及過期道具轉換提示。說話者名稱為符號的 Holo House 禮物交付畫面已通過離線回放。

能量仍為正數但不足時，只有讀到明確的不足規則，並在開始前確認相同餘量及有效的名目或實際消耗，才可使用剩餘能量；預算及內建 Auto 檢查仍然適用。此路徑僅通過離線驗證，仍待全程錄影原生實測，不會補充資源。

料理與跳繩已連接獨立遊玩模組。實測時關閉「僅驗證互動入口」、自行填寫局數；消耗上限留白代表不另設本次預算，填0則只允許實際零消耗。料理／跳繩的倍率0可明確選擇零能量模式。因預算不足而未開局時，介面會顯示任務未通過，日誌保留實際消耗、餘量與設定上限。跳繩停止分數留白會沿用模組的正常結束條件。

登入獎勵可依登入獎勵標題及頁面下方的繼續／空白處提示，自動點擊提示所在的空白區域，不依賴角色插圖、活動圖案或介面顏色。已確認登入或換日後，標題無法辨識的新插圖可使用明確的繼續提示接續；其他未知遊戲畫面不會套用此處理。相同版面的不同獎勵頁以文字區分，未改變的頁面不重複點擊，每段最多處理12頁。新加入的泛用辨識已通過離線測試，不同登入版面的實際啟動流程仍待使用者測試。

料理、單人 Live 與多人 Live 的局數分別由使用者填寫。釣魚使用參考錄影中的第二個釣點；每日限次項目可只驗證互動入口，不消耗遊玩次數。

執行實測時須先啟動遊戲視窗錄影，並保留時間對齊的步驟日誌；錄影故障會停止後續操作並釋放已按住的按鍵。錄影僅存本機，開發環境存於暫存程式旁的 `recordings` 目錄。每日限次內容的完整測試使用04:05（UTC+8）後的新次數，遊戲於04:00換日。

全程錄影的恢復測試已驗證換日提示、萬聖節與一般登入獎勵、收到獎勵頁，以及十一月會員公告。各已辨識頁面只確認一次，再等待下一個狀態；目前採分段恢復驗證，單次不中斷的換日流程仍待測試。其他公告版面會停止並等待驗證。

遊戲須已開啟。標題頁的登入與 TAP TO START 已分段通過錄影驗證；從 TAP TO START 開始，已能導航至樂園並完成一局 Auto Live。兩段標題步驟的單次不中斷流程仍待測試。

目前已在實際遊戲中驗證第二釣點「菈米的冰天雪堡」的地圖選擇、移動、有限距離接近及釣魚設定入口。從該設定頁開始的全程錄影實測，已使用無限練餌釣獲三尾魚；隨後的不中斷實測也已從樂園出發，在該釣點釣獲一尾魚、達標停止並返回樂園。其他魚餌尚未啟用。地圖卡片須確認地點名稱後才移動，並處理玩家標記遮住釣點圖示的情況。

料理已通過單次不中斷的全程錄影消耗能量單局與零消耗兩局實測，驗證獨立 DirectML 推論、各局開局前的新資源授權、穩定的分數與料理數字、領獎及返回設定畫面。消耗能量單局結果為7,210分、九道料理；零消耗兩局分別確認9,240／8,160分、十一／十道料理，不以內部訂單計數代替結算結果。跳繩已通過單次不中斷的全程錄影單局實測，驗證十分停止設定、開局前的新資源授權、分數與獎勵確認、後續活動頁及返回設定畫面；緊接的領獎任務也驗證了從小遊戲直接返回樂園。跳繩也已通過不中斷的零消耗兩局錄影實測，逐局取得子程序授權並確認返回。使用者設定以獨立 Maa 節點保存，並以原生整合檢查確認局數與消耗上限不會被後續介面選項覆寫。

樂園背景變動導致小字無法辨識時，小遊戲導航可改為確認手把圖示。仍須先確認樂園畫面；文字出現多個候選時不會改用圖示點擊。

料理與跳繩可明確設定為零能量；倍率視窗及準備頁的實際消耗均須讀到0，資源餘量仍須有效。料理兩局錄影實測在仍有能量時使用零資源預算完成。此選項與 Live 的正數消耗倍率分開處理。

High & Low 已通過全程錄影的地圖導航與互動入口驗證。流程會選擇電玩巨蛋城的遊玩區域分頁，確認 Shiori 的遊戲桌後傳送，並停在互動提示；尚未開啟或遊玩每日遊戲，可設定上限的模組整合仍待完成。

單人 Live 已分別通過消耗一點、九點與零點能量的全程錄影單局實測，以及不中斷的兩局實測，每次開歌前分別重新確認內建 Auto、資源及剩餘預算。資源預算填 0 時，只有已觀察到實際消耗為 0 才能遊玩，不會補充體力或略過 Auto 次數檢查；遊戲的消耗倍率仍須為正數。目前須沿用現有歌曲、難度與隊伍。多人 Live 已通過從樂園到模式選擇頁的全程錄影導航驗證；匹配、準備／開歌入口及多人遊玩仍未驗證與啟用。

Live 結果流程會先檢查已收到的 GET 頁與達成獎勵明細，再前進，過場畫面則等待辨識，避免猜測操作；兩局錄影實測已驗證這兩種額外獎勵。下一步的穩定判定以按鈕本身為範圍，持續播放的角色與評級動畫不會阻擋流程。

holoWork 已通過單次不中斷的全程錄影收取與重新派遣實測，確認收到報酬、沿用隊伍設定及新的倒數計時，同時保留原有進行中的工作。完全空白的隊伍可使用遊戲內建推薦，可見隊伍僅部分填好時會保留並停止檢查；沒有完成通知時會略過此任務。

三處樂園禮物已通過單次不中斷的錄影實測，確認三次 GET 及返回。路線會等待傳送過場及短暫圖示動畫，並支援每日角色變更；鏡頭依實際標記位移校準，每次最多40像素、最多12次，標記未朝正確方向移動時會停止。換日後抽獎也已通過從入口、對話、刮開一次、確認 GET 到返回樂園的不中斷錄影實測。

每日限次紀錄會在第一次互動前保存。失敗的抽獎嘗試只有在開場對話仍開啟，且確認原錄影已結束及新錄影正常後，才能接續一次。Holo House 還須核對同一遊戲視窗、交付台詞、名牌及周圍畫面。禮物接續檢查已通過離線測試。無法確認原對話仍開啟的嘗試會鎖定到下一個遊戲日，搜尋其餘禮物地點時也會排除已嘗試項目。

集中領獎會檢查每日、每週與賽季任務、通行證、成就、禮物箱，以及目前活動的每日與自由任務。單次不中斷的全程錄影實測已確認領取七組可用獎勵，包含活動實際獎勵，最後返回樂園。領取按鈕只點擊一次，確認收到獎勵或按鈕停用後才繼續；無可領獎勵時的檢查也已驗證，後續活動版面須另行驗證。

不同開發／測試版本可在本機 `config/recording.json` 指定相同的 `attempt_directory` 絕對路徑，共用每日限次紀錄，避免換版本後重複嘗試；啟用前須保留並合併既有紀錄。`tools/stage_dev.py` 對同一工作目錄下的版本使用共同紀錄目錄。未指定時仍沿用該程式原有的資料目錄，不會自行搬移紀錄。

## 開發

多人倒數保護已獨立實作，尚未接入或啟用配對。保護元件以獨立監督程序保存遊戲與親程序的控制代碼；未知／過期畫面不能延長截止時間，準備畫面不能回退為配對階段，最終 Auto 授權前失聯或中止會要求關閉受控遊戲。檔案讀寫執行緒與截止處理分開。每局須取得重新確認資源與 Auto 的授權，送出開始操作前再次檢查，並在輸入確認後才解除保護；多人開始呼叫缺少監督程序時會被阻擋。單人與受監督的多人流程都會在送出開始輸入前再次檢查觀察到的 Auto。

原生元件檢查已驗證獨立啟動及未啟用倒數保護的握手，沒有關閉遊戲。另一項測試只操作自建測試程序，確認監督程序能在測試父程序結束後繼續運作並關閉測試程序；阻塞讀寫測試則使用模擬遊戲。這些檢查尚未驗證實際多人倒數導航、遊玩期間關閉遊戲，或緊急關閉後的輸入釋放；完整多人流程維持停用，等待這些檢查完成。

四張多人錄影畫面已通過實際 Maa OCR 回放，正確辨識準備畫面及 30、27、25、21 秒倒數。共用插圖造成模板誤判時，以固定標題、AUTO 文字及難度標籤區分選曲與準備畫面。倒數證據本身不會授權開始；Auto 開關受遮擋或資源餘量無法讀取時仍會被阻擋。

獨立監督程序管理使用本地控制器的點擊子程序。點擊子程序的原生就緒檢查取得 1280×720 畫面，全程未派送點擊。模擬整合測試要求開始點擊的序號相符且確認輸入已釋放，監督程序才解除保護。測試也涵蓋親程序結束、管線阻塞，以及確認子程序結束後才釋放其獨占的右 Alt 和滑鼠左鍵。監督程序意外退出時的清理及原生緊急輸入釋放仍待驗證。多人配對維持停用。

`runtime-packages.lock.json` 鎖定 CPython 可內附壓縮檔，以及主程序與小遊戲各自使用的套件中繼資料版本。`tools/prepare_portable_runtime.py` 先核對已安裝套件的檔案雜湊，再複製必要檔案，排除本機中繼資料及位元碼，並進行不操作遊戲的匯入檢查；明確指定的模組路徑不會讀入使用者套件。

`tools/build_development_bundle.py` 接受鎖定的 GUI 壓縮檔及兩套已準備的執行環境，要求原始碼已提交且乾淨，保留鎖定的上游程式與模型識別，並產生檔案雜湊清單。輸出須為新目錄；首次啟動前可用 `--verify --output <測試包>` 核對，後續產生的設定與日誌會改變初始清單。本機開發測試包仍須具備 .NET10 與 Microsoft Visual C++ 執行階段，不代表已發布二進位版本或完整日常已驗收。

在具備 DirectML 的 Windows 電腦上，建立或核對初始測試包時可加入 `--check-modules`，載入複製後的料理與跳繩依賴並預熱模型，全程不輸入遊戲操作；兩項檢查均已通過。重建的開發測試包已通過料理與跳繩各一局原生遊玩，兩段影片均完整解碼並確認錄影先於遊戲輸入；也已驗證第二釣點兩尾釣獲。集中領獎的活動首頁改以固定控件文字確認，不依賴活動插畫及任務紅點圖示；已錄影驗證進入每日／自由任務、確認無可領獎勵及返回首頁，有可領獎勵時的新流程仍待驗證。

使用 Python 3.13 x64 與 .NET 10，安裝 `requirements-dev.txt` 後執行：

```powershell
python tools/build_resources.py
python tools/validate_resources.py
python -m pytest -q
```

複製專案時須包含子模組，`dependencies.lock.json` 記錄鎖定的上游提交。上游模組另需相應執行環境與模型，並與 Maa Agent 的環境分開。組件聲明見 `THIRD_PARTY_NOTICES.md` 及 `upstream/holodori/LICENSES.md`。

跳繩的獨立 Python 環境可安裝 `requirements-modules-jump.txt`，再執行 `python tools/check_jump_runtime.py`。此檢查只預熱 DirectML 模型，不操作遊戲；可用 `--sample` 指定本機遊戲畫面，驗證繩索與玩家標記辨識。開發機已通過十五張預熱畫面及三張參考畫面檢查，尚不代表遊玩時機已驗收，也不會啟用任務模組。

跳繩子程序每局取得第一張畫面後，須另經主程序核准；主程序重新確認實際消耗、資源餘量與預算後才開始。模組銜接測試涵蓋就緒、取消與過期授權拒絕，原生實測已驗證握手及設定的停止分數。選填停止分數接受1至999，零能量跳繩也已通過不中斷的兩局原生實測驗收。

料理模型依鎖定版本的 `models-manifest.json` 準備。執行 `tools/prepare_cooking_models.py --source <包含 models 的目錄>`，會先核對全部檔案，再複製到模組忽略追蹤的資源目錄。獨立環境可安裝 `requirements-modules-cooking.txt` 並執行 `tools/check_cooking_runtime.py`。本機快取的十個模型檔均符合清單；四個選用模型的 DirectML 預熱及三張錄影畫面推論已通過，全程不輸入遊戲操作。每個遊玩子程序須先預熱及確認擷取，再取得單局授權；自然結束及穩定的結算數字均須確認。取消或主程序結束時會設定上游停止檔。
